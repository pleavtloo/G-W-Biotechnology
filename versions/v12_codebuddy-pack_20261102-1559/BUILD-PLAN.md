# 从设计稿到可上线官网 —— 开发方案

> 现状：13 个页面（11 业务页 + 2 设计评审页）、90 个 PDF、AI 客服外壳。
> 全部由 Python 脚本生成静态 HTML，零运行时依赖。
> 结论：**设计层已经完成，缺的是「业务层」和「运营层」**。

---

## A. 决策（已锁定 2026-11-02）

| 项 | 决定 | 对方案的影响 |
|---|---|---|
| 语言 | **仅英文** | 去掉 i18n 工作流，省 1–2 周；不设 `/zh/`，不做 hreflang |
| 价格 | **公开** | 产品页保留起价与订购表；GMP / 大宗仍走询价 |
| AI | **仅 P1 检索问答** | 不做语音、不做数字人、不做实验设计建议；P2/P3 暂缓 |
| 部署 | **境外** | Cloudflare Pages + Worker；不需要 ICP 备案，上线周期短 2–3 周 |

由此带来的三条硬约束：

1. **英文文案必须一次写对**。没有中文兜底，翻译问题会直接暴露给客户。
2. **公开价格意味着价格表就是承诺**。涨价要走「历史报价有效期」，页面上的 `priceValidUntil` 已经写进结构化数据。
3. **P1 的边界要写清楚**。检索问答能回答"有什么、在哪、什么规格"，不能回答"我该用哪个"——后者是 P2，必须转人工。

## 1. 三条可选技术路线

| | A. 静态 + 轻后端（推荐） | B. 静态 + Headless CMS | C. 全栈框架（Astro / Next） |
|---|---|---|---|
| 做法 | 保留 Python 生成器，表单/AI/COA 走独立 API | 内容迁到 CMS，构建时拉取 | 整体重写为组件化 SSR/SSG |
| 适合 | 内容稳定、以获客为主 | 市场部要自己改产品与文章 | 多语言 + 会员 + 数据看板 |
| 周期 | **4–6 周** | 6–8 周 | 8–12 周 |
| 运维成本 | 极低（纯静态 + 2 个函数） | 低（多一个 CMS 订阅） | 中（Node 服务、构建流水线） |
| 迁移风险 | 无（增量） | 中（内容模型重做） | 高（重写） |
| 何时该升级到它 | — | 每月改内容 > 5 次 | 页面 > 25 或要做多语言 + 登录 |

**建议：走 A，但把内容层做成可迁移的。** 现在 `content.py` 已经是单一数据源，把它导出成
YAML/JSON，将来换 CMS 或换框架都只是换「渲染器」，内容不用重写。

**升级触发条件（写死在这里，避免以后拍脑袋）**：
- 需要 3 种以上语言 → 换 Astro
- 需要客户登录看订单/COA → 换 Next.js + 数据库
- 市场部要求自己发文章 → 加 CMS，不必换框架

## 2. 目标架构（路线 A）

```
                    ┌──────────────────────────────┐
   浏览器  ────────► │  CDN（Cloudflare Pages / COS）│
                    └──────────────┬───────────────┘
                                   │ 静态资源
                    ┌──────────────▼───────────────┐
                    │ dist/  13 页 + assets + docs │
                    └──────────────────────────────┘
                                   ▲
                    构建时生成      │
        ┌──────────────────────────┴──────────────────┐
        │  build_site.py  +  build_docs.py            │
        │  数据源：content/（YAML，从 content.py 导出）│
        └─────────────────────────────────────────────┘

   运行时三个轻服务（各自独立，互不阻塞）：
   ① /api/lead      询价、经销商申请、COA 查询 → 邮件 + CRM
   ② /api/chat      AI 客服 → 向量检索 → LLM → 引用 + 转人工
   ③ /api/coa       按批次号查 COA（对象存储 + 索引表）
```

**为什么拆成三个函数而不是一个后端**：表单挂了不影响 AI，AI 挂了不影响询价。B2B 站点最贵的
错误是「询价表单挂了三天没人发现」。

## 3. 工作分解（按可并行的工作流）

### W1 · 内容与素材（阻塞项，最先做）

| 项 | 谁给 | 交付物 |
|---|---|---|
| 42 个 SKU 真实规格 | 产品/QA | 每 SKU：纯度、内毒素、保存条件、分子量、表达系统 |
| 价格策略 | 商务 | 是否公开起价、GMP 溢价规则、区域价差 |
| COA 模板与真实批次样例 | QA | 1 份可公开的样例（脱敏） |
| DMF 表述授权 | 法规 | 可公开的文号范围 + 授权信流程 |
| 产品图 | 市场 | 每 SKU 白底图 ≥ 2000px，或授权用现有替代图 |
| 专家信息 | HR/本人 | 英文名、头衔、照片、前雇主可署名范围 |
| 合作机构 | 商务 | 是否可公开点名（涉及授权，默认不点名） |
| 公司主体信息 | 法务 | 注册名、地址、注册号、隐私政策与条款文本 |

> 内容不冻结，后面所有工作都会返工。**建议设一个「内容冻结日」，冻结前只改文字不改结构。**

### W2 · 前端工程化（1–2 周）

- [ ] 拆出 `content/` YAML（products / categories / applications / services / faq / articles）
- [ ] 构建输出到 `dist/`，HTML 压缩、CSS 压缩、JS 打包 + 压缩
- [ ] 图片生成 `srcset`（现有图片只有单一尺寸，Retina 屏偏软）
- [ ] 加 `robots.txt`、`sitemap.xml`（由构建生成，页面数变化自动更新）
- [ ] 每页补 `og:` / `twitter:` / `canonical`，产品页加 `Product` 结构化数据，公司页加 `Organization`
- [ ] 404 页面
- [ ] 表单前端校验 + 失败态（现在只有成功态）
- [ ] 打印样式（B2B 客户会打印规格页给采购）

### W3 · 表单与业务后端（1 周，可与 W2 并行）

4 个表单 + 1 个查询，全部要有：入库、邮件、防刷、失败重试。

| 端点 | 触发 | 去向 |
|---|---|---|
| `/api/lead` | 询价、经销商申请 | 邮件到销售组 + 写 CRM + 自动回执 |
| `/api/coa` | 批次号查询 | 对象存储取 PDF，命中则签名 URL，未命中转人工 |
| `/api/subscribe` | CTA 订阅 | 邮件列表（需双确认） |

要点：
- 反垃圾：hCaptcha 或 Cloudflare Turnstile（无感）
- 邮件送达：发信域配 SPF / DKIM / DMARC，否则进垃圾箱
- 留痕：每次提交写日志（时间、IP 哈希、来源页、UA），用于争议时回溯
- 失败降级：API 挂了也要提示「请直接邮件联系 xxx」，不能白屏

### W4 · AI 客服（1–2 周，可与 W3 并行）

**本轮只做 P1**（已定）。P1 = 检索问答：能回答"有什么、在哪、什么规格、DMF 怎么说"，
不能回答"我该选哪个"。

| 期 | 能力 | 状态 |
|---|---|---|
| P1 | 检索问答：产品规格、文档位置、DMF 说明 | **本期做** |
| P2 | 实验设计建议（宿主、标签、密码子策略） | 暂缓 |
| P3 | 语音与数字人 | 暂缓 |

P1 的实现要点：
- 语料 = 42 SKU 结构化数据 + 90 份 PDF 文本 + FAQ + 应用页文案
- 检索（向量 + 关键词混合）→ 取前 5 段 → LLM 只允许基于这 5 段作答
- 回答必须带来源链接；检索置信度低直接转人工
- 前端已有面板与转人工入口，只需把 `/api/chat` 从 501 换成真实实现

硬要求（写进验收）：
- 每条回答带**来源链接**（datasheet / FAQ / 文档）
- 覆盖不到就转人工，**不允许编造**
- 全量对话留存 ≥ 6 个月，供质量与合规抽查
- 面板常驻 `AI-generated · verify before use`
- 医疗/临床相关问题强制拦截并转人工

### W5 · 文档系统（1 周，与 QA 强耦合）

现在的 COA 是「每 SKU 一份代表性文件」。正式做法二选一：

- **方案甲（轻）**：COA 由 QA 签发后上传对象存储，命名 `coa-<sku>-<lot>.pdf`，建索引表
- **方案乙（重）**：接 LIMS，查询实时生成

建议先做甲。要点：
- 文件命名与索引表是唯一真相，页面不硬编码路径
- 版本管理：旧版本保留但标记 superseded
- 未签发的批次不对外，查询时返回「请联系 QA」

### W6 · ~~多语言~~（已取消）

不做中文版。省下的 1–2 周投到 P1 知识库与内容校对。
注意：英文文案现在是唯一版本，拼写与术语错误没有第二语言兜底，**校对必须走人工**。

### W7 · 部署与运维（3–5 天）

| 项 | 建议 |
|---|---|
| 托管 | 海外：Cloudflare Pages；境内：腾讯云 COS + CDN（需 ICP 备案） |
| 域名 | 主域 + `www` 301 到主域，HTTPS 强制 |
| 环境 | `staging.` 子域做预发，与生产同构建 |
| CI | GitHub Actions：构建 → 链接检查 → Lighthouse CI → 自动部署 preview |
| 监控 | Sentry（前端错误）+ UptimeRobot（5 分钟探活）+ 表单失败告警到群 |
| 备份 | 内容与文档每日快照，保留 30 天 |

### W8 · 合规与分析（3 天）

- Cookie 同意（仅必要项默认开启，分析需同意）
- 隐私政策、使用条款、可接受使用（AI 部分单独说明）
- 分析：Plausible 或 GA4，埋 6 个转化事件（询价、COA 查询、文档下载、AI 对话、经销商申请、电话点击）
- Search Console / Bing 验证

## 7. 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 内容迟迟不齐 | 上线延期，代码空转 | 设内容冻结日；先用「待确认」标注上线，后补 |
| 规格写错 | 客户投诉、法规风险 | 规格只由 QA 提供，文案不得自行推断 |
| COA 造假观感 | 信任崩塌（最严重） | 演示件必须标注 representative，正式件走 QA 签发 |
| AI 编造参数 | 合规与法律风险 | 强制引用来源、无源不答、全量留痕 |
| DMF 表述越界 | 法规风险 | 只写「已备案、可授权引用」，不写「获批」 |
| 多语言翻译失真 | 海外客户误解 | 术语表 + 母语审校，不用机翻直出 |
| 表单被刷 | 垃圾线索污染 CRM | Turnstile + 频率限制 + 人工抽检 |
| 单点故障 | 询价中断无人知 | 探活告警 + 邮件兜底路径 |
