## T&L 官网 v10：产品资料下载 + 搜索醒目化 + 第三条边界

### 1. 产品资料下载（本轮最大工作量）
用户要求"产品区域需要提供资料下载的地方"。原站点 Documentation 标签页全部指向
`contact.html#quote`，没有任何真实文件。

**做法**：写 `tools/build_docs.py`，用 fpdf2 生成 90 个 PDF 到 `website/docs/`。

| 文件 | 数量 | 页数 |
|---|---|---|
| `datasheet-<slug>.pdf` | 42 | 2（描述/订购表/规格/特性 + 使用保存/应用/兼容性/修订记录） |
| `coa-<slug>.pdf` | 42 | 1（批次号 + 8 项检验 + 放行声明 + 签字栏） |
| `sds-<cat>.pdf` | 4 | 2（16 节标准 SDS） |
| `dmf-summary.pdf` / `quality-overview.pdf` | 2 | 1 |

**关键实现**
- Calibri 从 `C:/Windows/Fonts` 加载，先用 pymupdf 的 `has_glyph` 验证 µ / ≤ / ⁺ / ® / α / β 全部存在，
  所以**不需要做字符替换**（之前用 ASCII 近似，出现 "10 ug"、"deg C" 很难看）
- 订单号 `TL-<族码>-<序号>`（BD/AB/PR/MD），批次号由 slug 的 md5 生成 → 重建不漂移
- 版式：深蓝页眉带 + 青色小节标题 + 斑马纹键值表 + 底部联系条

**踩坑**
- fpdf2 的 `multi_cell` 默认 `new_x=RIGHT`，标题后接副标题会从标题末尾续写，直接冲出右边界。
  所有标题调用必须显式 `new_x="LMARGIN", new_y="NEXT"`
- `kv_table` 用固定行高时，两行文本会溢出底色 → 改用 `dry_run=True, output="LINES"` 预测量
- 第一版 datasheet 第二页几乎是空的 → 补"应用/兼容性/修订记录"三节，两页都排满
- COA 外观字段对冻干品写成了"opalescent liquid" → 改为按 `specs["Format"]` 判断粉末/液体

**三处下载入口**：产品卡图右下角标 / 详情页 Documents 条 / `resources.html#docs` 文档库（4 卡 + 42 行表）

## v11：生产构建 + SEO + 表单 API（决策锁定后动工）

**用户锁定四项**：仅英文 / 公开价格 / AI 仅 P1 / 境外部署

**做了什么**

1. `tools/build_dist.py` —— 三级输出落地：`website/`（开发）→ `dist/`（部署）→ `versions/`（快照）
   - 自写 HTML/CSS 压缩（HTML -6%，CSS -22%）；JS 不压，保留可读性
   - 生成 sitemap.xml（52 URL：10 页 + 42 SKU）、robots.txt、`_headers`（HSTS/nosniff/缓存分级）、`_redirects`
   - 排除 `design-*.html`、README
2. `head()` 重写：canonical + OG + Twitter Card + 按页注入 JSON-LD
   - 全站 Organization；非首页加 BreadcrumbList；resources 加 FAQPage；contact 加 ContactPage
   - 产品页 Product + Offer 由前端按 slug 注入
   - `ld()` 用 `</` → `<\/` 转义，避免 JSON-LD 字符串里出现 `</script>` 提前闭合
3. 新增 404 页（noindex，四个去向 + COA lookup）
4. 表单从前端假提交改为真实 POST：
   - 三态（Sending… / 成功 / 失败），失败给 mailto 兜底
   - 字段名从 `<label>` 推导（原表单没有 name 属性）→ `full_name` / `work_email` / `organisation`
   - 蜜罐 `website_url` 静默 200，不报错
5. `server/worker.js`（Cloudflare Worker）：/api/lead /api/coa /api/chat(501) /api/health，
   16KB + 12 字段上限、Turnstile 可选、Resend 发信、不回显输入
6. `server/dev_server.py`：本地静态 + 真实 API，提交写 `server/outbox/*.jsonl`
7. 文档：BUILD-PLAN 加「决策锁定」「已完成」两节，时间表 6 周 → 5 周；
   DESIGN-LANGUAGE 加 9.3b 表单反馈、13.3 三级输出与 SEO 生成规则

**踩坑**

## v12：CodeBuddy 开发方案与提示词包

**用户诉求**：想用 CodeBuddy 开发这个项目，要方案 + 提示词。

**判断**：提示词写得漂亮没用，关键是三件套 —— 常驻约束 + 一次一件事 + 可执行验收。
所以产出不是"一段大 prompt"，而是一套工程化交接包。

**产出**
- `CODEBUDDY.md`（仓库根）：技术栈锁定、5 条命令、10 条硬规则（不改 dist、不编造规格、
  数量不写死、令牌不新增、AI 只 P1、失败必给 mailto、尊重 reduced-motion 等）、
  Definition of Done（build → check → 截图三件套）
- `codebuddy/README.md`：协作协议 —— 每轮开头三句话（读规约→读提示词→复述计划等确认）、
  上下文预算（明确"不要读 website/*.html，那是产物"）、7 种失败模式对照表
- `codebuddy/prompts/00–08.md`：9 份提示词，统一 目标/前置/任务/约束/验收/交付
- `tools/check.py`：新增质量门禁，48 项硬检查（链接、title/desc 唯一、canonical、og:image、
  h1 唯一、JSON-LD 可解析、dist 无 design 泄漏、sitemap/robots/_headers 齐全）
- 根 `README.md`：仓库索引

**关键设计**
- 提示词里把"已实现"与"待实现"分开写，避免 agent 重复造轮子（03 明确说骨架已有，只补四件事）
- 07 内容替换单独成篇，并写死"不许推断数值，缺就留空"——这是最容易出事的一步
- 08 验收给出 12 条手测场景与量化门槛，防止"看起来没问题"

**版本**：`versions/v12_codebuddy-pack_20261102-1600`
